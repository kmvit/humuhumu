# «Падача» — система управления кафе

Продукт для кафе и небольших ресторанов: меню по QR, заказы, экраны кухни и
бара, склад с себестоимостью, смены и зарплата, финансы. Открывается в браузере
и ставится на телефон как приложение (PWA).

Продаётся по подписке — [лэндинг padacha.ru](https://padacha.ru). Репозиторий
`humu` — это сам продукт; первое кафе-флагман «хумухумунукунукуапуа» работает
на нём каждый день.

## Как устроен SaaS

**Одна установка обслуживает все заведения.** Заведение опознаётся по домену
запроса, данные разделены на уровне каждой выборки (см. «Тенантность»).
Подключение нового клиента — строка в админке, а не развёртывание стека.

```
сервер (VPS с выделенным IP)
├── nginx хоста        — домены и сертификаты Let's Encrypt
└── общая установка    — 127.0.0.1:8082
    ├── humuhumunukunukuapua.ru  → заведение «Кафе»
    ├── monti.padacha.ru         → заведение «Монти»
    ├── demo.padacha.ru          → демо-стенд
    └── hub.padacha.ru           → служебный адрес админки

рядом, на том же сервере: лэндинг (статика) и ИИ-ассистент (:8100)
```

Раньше была схема «инстанс на заведение» — у каждой точки свой стек и своя
база. От неё отказались: десяток обновлений вместо одного, десяток баз для
бэкапа, и сборка образа на каждой точке. Инструменты переезда остались в
репозитории (`import_instance`, `purge_tenant`) — они же понадобятся, если
клиент захочет отдельную установку у себя.

**Подписки живут в самом продукте** — приложение `billing` (клиенты, подписки,
платежи), раздел в той же админке. Отдельный сервис-пульт, который был на
padacha.ru, переехал сюда командой `import_pult`.

### Тарифы

Тариф заведения — поле `SiteSettings.plan`, а что в него входит — один словарь
в [`backend/core/plans.py`](backend/core/plans.py). Вьюхи проверяют **фичу**, а
не тариф, поэтому перекройка тарифной сетки — правка одного словаря.

| Тариф | Фичи сверх базы |
|---|---|
| `start` | — (меню, QR-заказ, зал или стойка, оплаты, отчёты) |
| `hall` | `stations` — экраны кухни и бара |
| `max` | `+ inventory, shifts, finance, loyalty` — склад, смены, финансы, бонусы |

Тариф назначается **подпиской** (раздел «Подписки»), а `SiteSettings.plan`
приводится к ней автоматически. Для установки без подписок (отдельный инстанс
у клиента) тариф привозит сверка лицензии.

Фронт прячет разделы не по тарифу (`useFeature`), но настоящая защита —
permission-классы на бэке: без них клиент на «Старте» получил бы всё, дёрнув API.

### Тенантность

Заведение — сущность `core.Organization`, и у всех бизнес-моделей есть ссылка
на неё. Выборки идут через фильтрующий менеджер (`core/tenancy.py`), поэтому
фильтрация по заведению — поведение по умолчанию, а не дисциплина автора кода.

Текущее заведение выбирается **один раз, в `TenantMiddleware`, по домену
запроса**; дальше весь код берёт его из `current_organization()`. Если заведений
несколько, а текущее не выбрано (фоновая задача, команда), код падает с
`NoOrganizationSelected` — молча взять «первое попавшееся» значило бы показать
одному кафе данные другого.

- `TenantModel` — ссылка + фильтрация по умолчанию (`objects`), плюс
  `all_objects` без фильтра для поддержки;
- `TenantMixin` — только ссылка, для `User` (на нём вход и
  `createsuperuser`) и singleton-настроек;
- привязка проставляется в `save()` и в `bulk_create`, а на уровне БД
  поле обязательное — строк без заведения не бывает;
- логин, телефон гостя, стол, статья расходов, смена за дату и т. п. уникальны
  **внутри заведения**, а не глобально: «owner» и «Стол 1» есть у каждого кафе;
- вход и JWT работают в границах заведения (`users/auth.py`): токен, выданный на
  одном домене, на другом не действует;
- Django-админка фильтруется отдельным слоем (`TenantAdminMixin`) там, где
  менеджер модели намеренно не фильтрует — на `User` держится вход;
- `core.tests.TenancyGuardTests` не даёт новой модели появиться в обход, а
  `core/tests_isolation.py` пытается пробить границу всеми способами, какие
  даёт API: списком, по прямому id, правкой, ссылкой на чужой объект, через
  отчёты, с гостевой стороны и в админке.

**Чего стоит держаться при доработках:** не объявлять `queryset` атрибутом
класса во вьюсете (он вычислится один раз при импорте и «запомнит» чужое
заведение — только `get_queryset()`); в celery-задачах и командах явно
открывать `organization_context(...)`; новую глобально уникальную колонку
проверять на вопрос «а если у двух кафе это совпадёт?».

### Лицензия и блокировка

Заведение общей установки читает свою подписку **из той же базы** — сверяться
по сети с самим собой незачем.

Механизм лицензии остался для **внешних установок** (клиент на своём сервере):
такой инстанс раз в сутки (celery beat, 04:17) спрашивает `/api/license/` по
своему ключу, проверяет HMAC-подпись ответа и кэширует его в `LicenseState`.
Выдаёт лицензию `billing/views.py` — эндпоинт надтенантный, адресуется ключом,
а не доменом. Статус в обоих случаях считается **локально от текущей даты**:

```
active → expiring (за 5 дней) → grace (после «оплачено до»)
       → blocked (после грейса, 402 от LicenseMiddleware)
```

Фейл-опен намеренный: без ключа лицензирование выключено (автономная установка),
а блокировать можно только по сверке свежее 10 дней — недоступность выдающей
установки не должна останавливать чужую кухню. Открытыми при блокировке остаются гостевое меню, вход,
`/api/license/` (кнопка «Проверить оплату») и вебхуки банка.

## Подключение нового заведения

Ни сборки, ни отдельного стека — заведение заводится командой и живёт в общей
установке:

```bash
docker compose -f docker-compose.prod.yml exec backend \
    python manage.py new_tenant "Кофейня Компас" --domain kompas.padacha.ru --plan max
```

Команда создаёт заведение, его настройки и владельца `owner`, печатает пароль.

Порядок:

1. **DNS**: поддомен `*.padacha.ru` уже ведёт на сервер — ничего делать не надо.
   Свой домен клиента: A-запись на IP сервера.
2. `new_tenant` с нужным доменом и тарифом.
3. **Сертификат** — для домена вне `*.padacha.ru`:
   ```bash
   certbot --nginx -d домен-клиента.ru -d www.домен-клиента.ru
   ```
4. В админке завести клиента и **подписку** (раздел «Подписки») — от неё
   зависит тариф и блокировка за неоплату.
5. Отдать владельцу логин `owner` и пароль. Сотрудников он заводит сам:
   Админ-панель → «Сотрудники». **Django-админку клиенту не выдаём** — она
   наш инструмент поддержки.

Обновление продукта — одно на все заведения:

```bash
cd /opt/padacha-app && git pull --ff-only
docker compose -f docker-compose.prod.yml up -d --build
docker compose -f docker-compose.prod.yml restart web   # обязательно, см. грабли
```

### Переезд отдельной установки в общую

Если у клиента был свой инстанс — данные переносятся со сдвигом ключей:

```bash
# на переезжающей установке
python manage.py dumpdata --indent 1 catalog orders payments inventory \
    shifts finance wallet loyalty users core > instance.json
docker run --rm -v <проект>_media:/m alpine tar czf - -C /m . > media.tar.gz

# в общей установке
python manage.py import_instance instance.json --domain кафе.padacha.ru --media media.tar.gz
```

`purge_tenant --domain ... [--with-organization]` стирает данные заведения
послойно — чтобы переезд можно было переиграть.

## Стек

- **Backend:** Django 5 + DRF, PostgreSQL, Redis, Celery (+beat через `-B` у воркера)
- **Frontend:** React + Vite + TypeScript, PWA; CSS-переменные, без Tailwind
- **Оплата гостя:** интернет-эквайринг Т-Кассы или Сбера — банк выбирается в
  настройках заведения, ключи только в `.env` (`/api/site/` публичный)
- **ИИ:** распознавание накладных по фото (OpenRouter, gemini-2.5-flash)

## Структура

```
backend/
  config/        — настройки, urls, celery
  core/          — заведения и тенантность (tenancy.py, middleware.py),
                   настройки, тарифы (plans.py), лицензия (license.py),
                   брендинг PWA (branding.py); команды new_tenant,
                   import_instance, import_pult, purge_tenant
  billing/       — коммерческая часть: клиенты, подписки, платежи,
                   выдача лицензий внешним установкам
  users/         — пользователи, роли, вход в границах заведения (auth.py),
                   управление персоналом (staff.py)
  catalog/       — категории и товары
  orders/        — заказы, позиции, столы, режим стойки
  payments/      — эквайринг (acquiring.py) и терминал (providers.py)
  inventory/     — склад, тех. карты, приход по фото накладной
  shifts/        — смены, ставки, штрафы
  finance/       — расходы, ведомость, прибыль
  loyalty/       — бонусы гостям
  wallet/        — кошелёк и токены (наследие первого кафе)
frontend/src/
  pages/         — экраны по ролям: client, waiter, counter, kitchen, bar,
                   warehouse, shifts, finance, admin, legal
  components/    — Layout, LicenseGuard, ui/ (Modal, Toast, Stepper)
deploy/
  new-cafe.sh    — развернуть ОТДЕЛЬНУЮ установку (клиенту на свой сервер)
  nginx.conf     — nginx внутри контейнера web
  Dockerfile.web — сборка фронта + nginx
```

Роли: `client`, `waiter`, `cook`, `bar`, `warehouse` (менеджер: склад, смены,
финансы), `admin` (владелец). Формат обслуживания — настройка
`SiteSettings.service_mode`: `hall` (зал с официантами) или `counter` (стойка с
выдачей по номеру); во втором у официанта другой экран, а заказ получает
дневной номер.

## Продакшн

`docker-compose.prod.yml`: db, redis, backend (gunicorn), worker (celery + beat),
web (nginx + собранный фронт), опционально tunnel (SOCKS5 для OpenRouter из РФ).
Backend на старте сам делает `migrate` и `collectstatic`.

`WEB_BIND` решает, как отдаётся сайт: `127.0.0.1:<порт>` — когда домены и
сертификаты разводит nginx хоста (так работает общая установка),
`0.0.0.0:80` — когда стек на сервере один.

`ADMIN_HOST` — служебный адрес админки (`hub.padacha.ru`): по нему заведение
выбирается переключателем «Работать от имени», а не доменом. По домену
заведения админка тоже открывается — и показывает только его данные.

**HTTPS наш**: сертификаты Let's Encrypt на сервере (`certbot --nginx`),
продление автоматическое. Это и позволяет подключать клиентские домены без
участия панели хостинга.

Демо-стенд — тот же продукт с флагом `DEMO_STAND=1` и командой
`seed_demo_stand` (стирает базу, поэтому без флага не работает).

## Грабли

Собрано кровью, не наступать повторно:

- **Прокси хостинга перед VPS** пропускает только домены, привязанные в его
  панели: чужой Host получает 404 и **в логи сервера не попадает вовсе**.
  Лечится отключением проксирования и выделенным IP — тогда трафик идёт прямо
  к нам и сертификаты выпускаем сами. Проверка, доходит ли запрос:
  `curl http://домен/probe-123` и `grep probe-123` в access.log; кириллица в
  URL кодируется, поэтому метку брать латиницей.
- **Домен из чужого аккаунта хостинга** не обслужить ничем: ни DNS, ни
  выделенный IP не помогают, пока домен не перенесён в нужный аккаунт.
- **Сертификат с лишним доменом**: если удалить DNS-запись домена, который
  входит в общий сертификат, автопродление упадёт для ВСЕХ доменов оттуда.
  Сначала перевыпустить (`certbot certonly --cert-name ... -d ...`), потом
  убирать запись.
- **`default_server`**: без блока-заглушки nginx отдаёт первый попавшийся сайт на
  любой Host — приложение светилось на техадресе VPS. На обоих серверах роль
  `default_server` отдана блоку `default-deny` с `return 444`.
- **502 после пересборки backend**: nginx контейнера `web` резолвит имя
  `backend` один раз при старте и держит старый IP. Лечится `restart web` —
  добавляйте эту команду в конец каждой выкатки, иначе забывается.
- **Прод-образ копирует код внутрь** (`COPY . .`), поэтому `git pull` на сервере
  сам по себе ничего не меняет — нужен `up -d --build`.
- **pypi.org недоступен с jino**: для сборки задать
  `PIP_INDEX_URL=https://pypi.tuna.tsinghua.edu.cn/simple`.
- **Сборка идёт 10–15 минут, ssh-сессия рвётся** и уносит с собой
  `docker compose up`. Запускать отцепленно через `nohup`, потом опрашивать лог.
- **`curl http://localhost/api/...` с сервера даёт 400** (DisallowedHost) —
  проверять через публичный домен или с `-H "Host: ..."`.
- **`queryset` атрибутом класса во вьюсете** вычисляется при импорте и
  «запоминает» заведение, которое было текущим тогда. Только `get_queryset()`.
- **Переезд установки**: пути к файлам растут на префикс `org-<id>/`, поэтому
  поля под них — 200 символов; у заведения уже есть пустые настройки-заглушки,
  импорт их удаляет; заведение нельзя удалить каскадом (внутри защищённые
  связи) — для этого `purge_tenant`.
