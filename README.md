# «Падача» — система управления кафе

Продукт для кафе и небольших ресторанов: меню по QR, заказы, экраны кухни и
бара, склад с себестоимостью, смены и зарплата, финансы. Открывается в браузере
и ставится на телефон как приложение (PWA).

Продаётся по подписке — [лэндинг padacha.ru](https://padacha.ru). Репозиторий
`humu` — это сам продукт; первое кафе-флагман «хумухумунукунукуапуа» работает
на нём каждый день.

## Как устроен SaaS

Один инстанс на заведение («мультиинстанс»), а не общая база на всех: у каждой
точки свой контейнерный стек, своя БД и свой домен. Настоящий мультитенант не
делали намеренно — при десятках клиентов изоляция данных, свой часовой пояс и
независимые обновления достаются бесплатно, а переписывать 8 тыс. строк не надо.

```
padacha.ru (сервер-центр)
├── лэндинг                    — статика
├── ИИ-ассистент               — :8100
└── ПУЛЬТ  /pult/              — :8110, реестр клиентов и подписок
    └── /api/license/          — сюда ходят инстансы заведений

серверы с инстансами (тот же или отдельные VPS)
├── host nginx                 — разводит домены
├── /opt/<кафе-а>  → 127.0.0.1:8081   своя БД, свои тома
└── /opt/<кафе-б>  → 127.0.0.1:8082
```

Пульт живёт в **другом репозитории** — `padacha-landing`, папка `pult/`
(Django + SQLite + админка). Там заводятся клиенты, точки и платежи.

### Тарифы

Тариф заведения — поле `SiteSettings.plan`, а что в него входит — один словарь
в [`backend/core/plans.py`](backend/core/plans.py). Вьюхи проверяют **фичу**, а
не тариф, поэтому перекройка тарифной сетки — правка одного словаря.

| Тариф | Фичи сверх базы |
|---|---|
| `start` | — (меню, QR-заказ, зал или стойка, оплаты, отчёты) |
| `hall` | `stations` — экраны кухни и бара |
| `max` | `+ inventory, shifts, finance` — склад, смены, финансы |

Фронт прячет разделы не по тарифу (`useFeature`), но настоящая защита —
permission-классы на бэке: без них клиент на «Старте» получил бы всё, дёрнув API.

### Тенантность (подготовка к общей базе)

Сейчас каждая точка живёт в своей базе, но код к общей уже готов:
у всех бизнес-сущностей есть ссылка на `core.Organization`, а выборки идут
через фильтрующий менеджер (`core/tenancy.py`). Пока в каждой базе ровно
одна организация — ошибиться фильтром не во что, соседей физически нет.

- `TenantModel` — ссылка + фильтрация по умолчанию (`objects`), плюс
  `all_objects` без фильтра для поддержки;
- `TenantMixin` — только ссылка, для `User` (на нём вход и
  `createsuperuser`) и singleton-настроек;
- привязка проставляется в `save()` и в `bulk_create`, а на уровне БД
  поле обязательное — строк без заведения не бывает;
- `core.tests.TenancyGuardTests` не даёт новой модели появиться в обход.

**Что останется при переезде на общую базу:** научить
`current_organization()` определять заведение по запросу (домен или
членство) вместо «она одна»; сделать логины уникальными в пределах
заведения, а не глобально; развести singleton-настройки
(`SiteSettings`/`ShiftSettings`/`LicenseState` сейчас грузятся по `pk=1`)
по организациям; перенести данные из отдельных баз в общую.

### Лицензия и блокировка

С `LICENSE_KEY` в `.env` инстанс раз в сутки (celery beat, 04:17) сверяется с
пультом: проверяет HMAC-подпись ответа, кэширует «оплачено до» в `LicenseState`
и пишет тариф в настройки. Статус считается **локально от текущей даты**:

```
active → expiring (за 5 дней) → grace (после «оплачено до»)
       → blocked (после грейса, 402 от LicenseMiddleware)
```

Фейл-опен намеренный: без ключа лицензирование выключено (автономная установка),
а блокировать можно только по сверке свежее 10 дней — падение пульта не должно
останавливать чужую кухню. Открытыми при блокировке остаются гостевое меню, вход,
`/api/license/` (кнопка «Проверить оплату») и вебхуки банка.

## Подключение новой точки

На сервере, от root:

```bash
bash deploy/new-cafe.sh <slug> <домен> --license-key <ключ из пульта>
```

Скрипт: клонирует репозиторий в `/opt/<slug>`, генерирует `.env` со своими
секретами (`COMPOSE_PROJECT_NAME` изолирует контейнеры и тома от соседей),
поднимает стек на `127.0.0.1:<свободный порт>`, прописывает домен в nginx хоста,
заводит владельца `owner` и печатает его пароль, делает первую сверку с пультом.

Порядок подключения клиента:

1. В пульте `padacha.ru/pult/` завести клиента и точку — ключ лицензии
   сгенерируется сам.
2. DNS: A-запись домена на этот сервер; в панели хостинга привязать домен к VPS
   (иначе прокси jino не пропустит запрос — [см. грабли](#грабли)).
3. Запустить `new-cafe.sh` с этим ключом.
4. Отдать владельцу логин `owner` и пароль. Сотрудников он заводит сам:
   Админ-панель → «Сотрудники». **Django-админку клиенту не выдаём** — она
   наш инструмент поддержки.

Обновление инстанса:

```bash
cd /opt/<slug> && git pull --ff-only
docker compose -f docker-compose.prod.yml up -d --build
```

## Стек

- **Backend:** Django 5 + DRF, PostgreSQL, Redis, Celery (+beat через `-B` у воркера)
- **Frontend:** React + Vite + TypeScript, PWA; CSS-переменные, без Tailwind
- **Оплата гостя:** интернет-эквайринг Т-Кассы или Сбера — банк выбирается в
  настройках заведения, ключи только в `.env` (`/api/site/` публичный)
- **ИИ:** распознавание накладных по фото (OpenRouter, gemini-2.5-flash)

## Структура

```
backend/
  config/        — настройки, urls, celery
  core/          — настройки заведения, тарифы (plans.py), лицензия (license.py),
                   брендинг PWA (branding.py), middleware блокировки
  users/         — пользователи, роли, управление персоналом (staff.py)
  catalog/       — категории и товары
  orders/        — заказы, позиции, столы, режим стойки
  payments/      — эквайринг (acquiring.py) и терминал (providers.py)
  inventory/     — склад, тех. карты, приход по фото накладной
  shifts/        — смены, ставки, штрафы
  finance/       — расходы, ведомость, прибыль
  wallet/        — кошелёк и токены (наследие первого кафе)
frontend/src/
  pages/         — экраны по ролям: client, waiter, counter, kitchen, bar,
                   warehouse, shifts, finance, admin, legal
  components/    — Layout, LicenseGuard, ui/ (Modal, Toast, Stepper)
deploy/
  new-cafe.sh    — подключение новой точки
  nginx.conf     — nginx внутри контейнера web
  Dockerfile.web — сборка фронта + nginx
```

Роли: `client`, `waiter`, `cook`, `bar`, `warehouse` (менеджер: склад, смены,
финансы), `admin` (владелец). Формат обслуживания — настройка
`SiteSettings.service_mode`: `hall` (зал с официантами) или `counter` (стойка с
выдачей по номеру); во втором у официанта другой экран, а заказ получает
дневной номер.

## Разработка

```bash
cp .env.example .env
docker compose up --build
```

- Фронт: http://localhost:5173
- API: http://localhost:8000/api/
- Django-админка: http://localhost:8000/admin/

Демо-данные (пользователи `admin` / `cashier` / `anna` / `boris`, пароль
`demo12345`):

```bash
docker compose exec backend python manage.py seed_demo
```

Тесты (114 шт.). Локальный Postgres может быть занят чужим инстансом — тогда
через docker-сеть:

```bash

```

```bash
docker run --rm --network humu_default --env-file .env -e DJANGO_DEBUG=1 \

```

## Продакшн

`docker-compose.prod.yml`: db, redis, backend (gunicorn), worker (celery + beat),
web (nginx + собранный фронт), опционально tunnel (SOCKS5 для OpenRouter из РФ).
Backend на старте сам делает `migrate` и `collectstatic`.

`WEB_BIND` решает, как отдаётся сайт: `0.0.0.0:80` — одиночная установка,
`127.0.0.1:<порт>` — когда на сервере несколько заведений и домены разводит
nginx хоста.

Демо-стенд — тот же продукт с флагом `DEMO_STAND=1` и командой
`seed_demo_stand` (стирает базу, поэтому без флага не работает).

## Грабли

Собрано кровью, не наступать повторно:

- **Прокси jino** пропускает на VPS только домены, привязанные к нему в панели.
  Чужой Host получает 404 и в логи сервера не попадает. Проверка:
  `curl --resolve домен:80:IP` — если 404 и в логе пусто, дело в панели.
- **`default_server`**: без блока-заглушки nginx отдаёт первый попавшийся сайт на
  любой Host — приложение светилось на техадресе VPS. На обоих серверах роль
  `default_server` отдана блоку `default-deny` с `return 444`.
- **502 после пересборки backend**: nginx контейнера `web` резолвит имя `backend`
  один раз при старте и держит старый IP. Лечится `restart web`.
- **Прод-образ копирует код внутрь** (`COPY . .`), поэтому `git pull` на сервере
  сам по себе ничего не меняет — нужен `up -d --build`.
- **pypi.org недоступен с jino**: для сборки задать
  `PIP_INDEX_URL=https://pypi.tuna.tsinghua.edu.cn/simple`.
- **Сборка идёт 10–15 минут, ssh-сессия рвётся** и уносит с собой
  `docker compose up`. Запускать отцепленно через `nohup`, потом опрашивать лог.
- **`curl http://localhost/api/...` с сервера даёт 400** (DisallowedHost) —
  проверять через публичный домен или с `-H "Host: ..."`.
